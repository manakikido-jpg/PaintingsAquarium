# 動物園：実スキャン前に決めること

2026-11-12。会場配布前のテスト版用。合成画像の合格率を、イベントでの発生率には置き換えない。会話中の「5〜15%」は準備時間のための主観的な仮置きであり、実測の故障率ではない。

## 先に固定する設定

| 対象 | 初回テストの設定・確認 |
|---|---|
| アプリ | 動物園の修正入りテスト版。版番号・設定値を記録する |
| 印刷 | 同梱のA4横PDFを等倍・片面。台紙を描き直さない |
| 保存形式 | カラーJPEG高画質またはPNG。PDF不可 |
| 解像度 | まず300dpi。遅ければ150dpiと同じ原稿で比較する |
| 画像補正 | 強い地色除去・白黒化・輪郭強調は避け、薄い色の原稿で比較してから採用する |
| 保存先 | PC内の専用フォルダ。クラウド同期・ネットワーク共有・USBはまず避ける。アプリの取り込み先と一致させる |
| 保存名 | 日時＋連番で別名保存。同名上書きも対応するが、元スキャンを残すには別名が必要 |
| 電源 | AC接続、会期中のスリープを停止。スキャナの休止復帰も試す |
| 表示 | 会場で使うモニターと解像度。しっぽオフ・背景の強さ0を復旧時の候補にする |
| 保全 | 既存の絵と設定をバックアップ。失敗した元画像は加工せず残す |

## 実スキャンでの確認順

1. 普通に塗った6種を1枚ずつ通す。種類・向き・切り抜き・サイズ・足・しっぽを確認。
2. 薄塗り・濃い黒・余白の落書き・体につながるはみ出しを追加し、全6種で比較する。設定は一度に1項目だけ変え、普通の6枚も再検査する。
3. 会場の速度で10〜20枚連続スキャン。保存ファイル数とアプリの一覧件数を照合。画面は最新の表示数までなので、画面上の体数だけでは取り込み漏れを判定しない。
4. 同名上書き、紙を90度回す、スキャナの休止から復帰、アプリの再起動を試す。アプリ終了中に保存した紙も起動後に入るか確認する。
5. 50体程度で最低3時間、できれば会期と同じ時間動かす。途中でも追加スキャンする。取り込みの遅延や停止が増えないか記録する。

保存完了から表示まで5秒以内を目標に測る。スキャナが紙を読む時間とは分ける。種類不明でも標準サイズで地面を歩けば、その点は正常。大きな接続線で本体が相対的に小さくなる問題は残る。

## 止まったときの順番

1. スキャン画像が保存先に実際にあるか、JPEG/PNGか、ファイルサイズが0でないかを見る。
2. アプリ側の取り込み先・選択テーマ・失敗通知を見る。
3. 元画像を残し、別のファイル名で1枚だけ再投入する。直った操作と所要時間を記録する。
4. 動きだけ不自然なら、しっぽをオフにして歩行を確認。重ければ背景の強さ・同時表示数を下げて比較する。
5. 保存データを消したり再インストールしたりする前に、バックアップと状況を残す。

`ファイル名／動物／画材・塗り方／スキャナ設定／表示までの秒数／問題／復旧操作` を記録する。問題の元画像と画面動画があれば、入力・切り抜き・判定・表示のどこで変わったかを追える。

## 開発側で追加確認したこと

同名・同サイズのPNGを、ゾウ→ライオン→キリンへ上書きし、再起動なしで3枚保存。更新日時も内容も同じ通知と監視再開では重複0枚。壊れた内容から正常画像への上書きでも次の絵が入った。これは実Electronと模擬ファイル書込みの検査であり、実スキャナの検査ではない。

587単体テスト、typecheck/build成功。検査スクリプトは `tools/audit-scan-overwrite.py`。書込みが400ms以上一時停止した後に再開する機種、保存中の電源断、元の更新日時も保持する上書きなどは追加確認が必要。
