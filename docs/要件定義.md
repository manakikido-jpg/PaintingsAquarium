# 要件定義

- プロジェクト名: PaintingsAquarium（お絵かき水族館）
- 最終更新: 2026-08-12

## 1. 何のための道具か

**会場スタッフの「絵を取り込んで映すまでの手作業」を無くす。**

紙に描いた絵を撮った写真を、決めたフォルダに入れる。それだけ。
アプリが勝手に見つけて、紙の白を透明にして、大画面の水槽で泳がせる。
**スタッフのアプリ操作は0回。**

## 2. 誰が使うか

| 使う人 | 端末 | 1日に何回触るか | この人にとっての「これがあれば嬉しい」 |
|---|---|---|---|
| 会場スタッフ | PC 1台（アプリを触るのはPCのみ。撮るのは iPad / カメラ） | 写真の取り込み 200回 ／ **アプリ操作は0回** | 写真を入れたら、何もしなくても泳いでいる |
| 運営者（あなた） | 同じPC | 1日 1〜3回 | 変な絵をすぐ消せる。今日の枚数が分かる |
| 来場者 | 触らない（**モニター**を見るだけ。プロジェクターではない） | — | 自分の絵が泳いでいるのがすぐ分かる |

> 200枚/日は想定値（D-2）。会期で実測したらこの表を更新する。
> **この表の「操作回数」が設計の根拠**であり、機能を足すときは必ずここに戻ること。

## 3. やること（スコープ）

| # | やること | なぜ必要か |
|---|---|---|
| 1 | 決めたフォルダを見張り、新しい画像を自動で取り込む | スタッフの操作を0回にするため。**ここが本体** |
| 2 | 紙の白を透明にする（明るさのしきい値のみ。AI不使用） | 白い長方形が泳ぐのを避ける。線の形も色も変えない |
| 3 | 紙の影やゴミの塊を捨てる | 照明ムラで紙の隅が残ると、外接矩形が絵の何倍にも膨らむ（R-003） |
| 4 | 絵の外周を自動でトリミングする | 余白のぶん、描画も当たり判定も無駄になる |
| 5 | 水槽で泳がせる（Canvas 2D） | これが見せたいもの |
| 5b | 背景と装飾（揺らぎ模様・光の筋・泡・砂地・サンゴ・貝殻・沈没船） | 無地だと展示として寂しい。**明るく鮮やかな青**にする（参考: teamLab のお絵かき水族館）。ただし色数の多い飾りは**画面の下に集め、絵が泳ぐ中央は綺麗な青のまま**残す。会場で強さを下げられるようにする |
| 5c | 絵どうしが避け合う | 重なると**自分の絵を探しに来た子どもが見つけられない**。この展示の核心 |
| 5d | 取り込んだ絵がふわっと現れる | いきなり出ると「湧いた」ように見える。水の奥から泳いで来たように見せる |
| 6 | 大画面に全画面表示する | 来場者が見るのはこれ |
| 7 | 一覧から絵を消せる | 不適切な絵・失敗した取り込みを人が消す |
| 8 | 完全オフラインで動く | 会場のネットに依存しない。**今回の大前提** |

## 4. やらないこと（スコープ外）

| やらないこと | なぜ／いつなら考えるか |
|---|---|
| **AIによる絵の補正・生成・自動審査** | 本人の明示指示。描いた絵をそのまま泳がせることが価値。審査は人が消す運用で始める |
| **Webへの公開（Vercel等）** | オフライン前提と両立しない。会期後に「見せる用」が欲しくなったら別プロジェクトとして考える |
| 来場者のスマホからの投稿 | 会場PCのみ。荒らし対策と、オフラインでは端末間の受け渡しを自前で作ることになるため |
| iPad側のアプリ画面 | 撮影は標準カメラで足りる。作るものを1つに絞る |
| アカウント・ログイン | PC1台の会場運用。要らない |
| 氏名・写真などの個人情報 | 最初の版では持たない。持つなら保管期間と削除の方針を先に決める |
| 台紙（四隅マーカー）の印刷運用 | 白しきい値＋塊の除去で始める。実物で精度が足りなければ再検討 |
| 水の物理シミュレーション・3D表現 | 背景は Canvas 2D の重ね塗りで作る。物理演算は入れない |
| **macOS 対応** | Windows のみにする。署名（年 $99）と公証の手間が、会場PC1台に対して見合わない。Electron なので後から戻せる |
| 印刷・グッズ化・多言語 | 今回の範囲外 |

## 5. 守らなければならないこと（非機能）

- **個人情報**: 持たない。保存するのは「絵の画像」と「取り込み日時」だけ。
  氏名・ニックネーム・顔が写った写真は入れない。
  （オフラインなので通信自体が発生しないが、それでも持たない方針は変えない）
- **止まったら困る度合い**: 会期中に1時間止まると、その間に描かれた絵が泳がない。
  ただし**元の写真は取り込みフォルダに残る**ので、復旧後にやり直せる。
  → 「取り込み済みの記録」を消せば再取り込みされる設計にする（F-104）。
- **同時に使う人数**: PC1台。スタッフ1〜数人が同じPCを触る。同時書き込みは考えない。
- **さばく量**: 200枚/日（D-2）。取り込み処理は1枚ずつ順番に行い、泳いでいる絵がカクつかないようにする。
- **データを失ったら**: `data/` を失うと泳いでいる絵が全部消える。
  ただし**取り込みフォルダの写真さえ残っていれば全部やり直せる**。
  → **取り込みフォルダを消さないことが唯一のバックアップ。** 会期終了までフォルダを消さない運用にする。

## 6. 用語

| 言葉 | 意味 |
|---|---|
| 水槽 | 絵が泳ぐ画面そのもの |
| 個体 | 水槽を泳いでいる絵1枚 |
| 取り込みフォルダ | アプリが見張っているフォルダ。ここに写真を置く |
| 透過 | 紙の白い部分を透明にすること。**AIではなく明るさのしきい値** |
| 会期 | 展示している期間 |

## 7. 前提・制約

- **使う技術**: Electron + TypeScript + Vite + React、水槽の描画は Canvas 2D、テストは Vitest
- **動かす場所**: 会場の PC 1台にインストール。**ネット接続は一切不要**
- **見せる画面**: **モニター**（プロジェクターではない）。
  黒がきちんと沈むので、背景は深く暗くしてよい。絵を浮き上がらせる設計にできる
- **保存先**: PCのローカルフォルダのみ（`data/` に画像、メタデータは JSON）
- **予算・期限**: 無料（外部サービスを使わないため運用費0）。期限は未定
- **既にあるもの**: なし（新規）

### なぜこの構成か（採らなかった案の理由も）

| 決めたこと | 採用 | 採らなかった案とその理由 |
|---|---|---|
| 実行形態 | Electron のデスクトップアプリ | **Tauri** も軽くて良いが Rust 環境が要る。**PWA** はフォルダの自動監視がブラウザ制限で弱く、「操作0回」が成立しない。ここは譲れない要件なのでアプリにした |
| 保存 | ローカルの JSON + 画像ファイル | SQLite は会期の想定枚数（数千）に対して過剰。JSON なら中身を人が読めて、壊れても直せる。書き込みは一時ファイル＋リネームで壊さない |
| 描画 | Canvas 2D | PixiJS（WebGL）は速いが依存が増える。まず Canvas 2D で作り、実測でコマ落ちしたら移す |
| 水面の揺らぎ模様 | 小さい面（長辺480px）に計算して引き伸ばす | 画面の実寸で画素ごとに三角関数を呼ぶと、4K でコマ落ちする。模様はもともとぼやけているので拡大しても粗が出ない。実測 1 フレーム 1.1ms |
| 透過 | 明るさ＋鮮やかさのしきい値、外周からの塗りつぶし探索 | AI背景除去は本人が明確に不採用。単純に「明るい画素を消す」だと絵の内側の白（目など）まで抜けて穴だらけになるため、外周から繋がった白だけを消している |
| 影・ゴミの除去 | 連結した塊のうち、縁に接するものと小さすぎるものを捨てる | 照明ムラで紙の隅が塊として残り、外接矩形が絵の3倍に膨らんだ（R-003）。局所的な明るさ補正のほうが原理的には正しいが、薄い色の絵まで消しかねず、テストで固定しづらい |

すべて回答済み（2026-08-12）。

| ID | 決めたこと | 結論 |
|---|---|---|
| D-1 | 実物の写真をもらえるか | **もらえない。** そのため、しきい値を設定画面のスライダーで調整できるようにした。運営者が会期前に1回合わせれば、通常運用の操作は0回のまま |

| D-3 | 絵の寿命 | **画面には最新50匹だけ泳がせ、全件は保存** |
