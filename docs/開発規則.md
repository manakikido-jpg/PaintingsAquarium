# 開発規則

守るべきことを `R-番号` で記録する。

**バグを踏んだら必ずここに残す。直して終わりにしない。**
書くのは次の3つ。これが揃っていないものは規則にならない。

1. **何が起きたか**（利用者から見て何が困ったか）
2. **なぜそうなったか**（表面の症状ではなく、本当の原因）
3. **今後どうするか**（次に同じ場面が来たとき、何を守るか）

一度振った番号は変えない。コメントやコミットメッセージから参照するため。

---

## 書き方の例

他プロジェクトから。この粒度で書けば役に立つ。

- **R-539 `backdrop-filter` を付けた要素は `position: fixed` の基準になる**:
  ヘッダーに `backdrop-filter` を付けていたため、その中の引き出しメニューが
  **ヘッダーの高さに閉じ込められて開かなかった**。
  画面全体に広げたい要素は `createPortal` で `document.body` の直下に出す。

- **R-563 画面下に固定して浮かせる要素は、必ず何かを塞ぐ**:
  「ホーム画面に追加」の案内を `fixed bottom-*` で出したところ、
  下部タブと送信ボタンに覆いかぶさり**押せなくなった**。
  案内は**通常の要素として本文に流し込む**。浮かせない。
  検証では、ボタンの中心に本当にそのボタンがあるかまで確かめる。

- **R-564 検証で邪魔な要素を消してはいけない**:
  通し検証のとき案内カードを消してから操作していたため、
  それがボタンを塞いでいることに気づけなかった。
  **利用者が最初に見る状態のまま**試すこと。

## 規則

- **R-001 「どこで動かすか」を聞いても、「ネットが無くても動く必要があるか」は出てこない**:

  **何が起きたか** — 「動かす場所は？」という質問に「Webに公開（Vercel等・HTTPS）」と
  回答をもらい、それを前提に Vercel + Supabase の設計を書いた。
  直後に「オフラインでも動く形にしたい」と言われ、**設計をまるごと捨てた**。

  **なぜそうなったか** — 質問が「どこに置くか」を聞いていて、
  「ネットが落ちても動く必要があるか」を聞いていなかった。
  置き場所を聞かれると、人は**希望**（公開したい）で答える。
  **制約**（ネットが無くても動かないと困る）は、それ単体で聞かないと出てこない。

  **今後どうするか** — 設計を始める前に、置き場所とは**別の質問として**次の2つを必ず確認する。
  1. ネットが落ちても動く必要があるか
  2. 外部サービス（DB・API・認証）に依存してよいか
  置き場所の質問で代用しない。

- **R-002 非同期の読み込みが終わる前に届いたものを、黙って捨ててはいけない**:

  **何が起きたか** — 取り込みフォルダに写真を入れても、**何のメッセージも出ないまま
  絵が泳ばなかった**。ログにも異常が出ず、監視は動いているのに結果だけが無かった。

  **なぜそうなったか** — 画面側で設定を読むのが非同期で、起動直後は `null` だった。
  写真が届いたときの処理に `if (!settings) return` と書いていたため、
  **設定が読み終わる前に届いた写真が全部そこで消えていた**。
  「まだ準備できていない」を「何もしない」で表現したのが誤り。

  **今後どうするか** — 外から届いたものを扱う処理で、準備が未完了だからと
  `return` して終わらせない。**待つ**（必要な値をその場で取り直す）か、
  **キューに積む**か、**理由を画面に出す**かのいずれかにする。
  黙って捨てる分岐を書かない。

- **R-003 白を透明にしただけでは、紙は消えきらない**:

  **何が起きたか** — 切り抜き自体は成功していたのに、水槽で絵が**極端に小さく**表示された。
  切り抜き後の画像を見ると、絵の右下に**紙の影が塊のまま残り**、
  外接矩形が絵の 3 倍近く（935×590、絵の実寸は 626×281）に膨らんでいた。

  **なぜそうなったか** — 照明が均一でないため紙の隅が暗くなり、
  明るさのしきい値を下回って「紙ではない」と判定された。
  しきい値は画像全体で同じ 1 つの値なので、明るさにムラのある写真では必ず起きる。

  **今後どうするか** — 透過のあとに、**連結した塊の単位で選別する**工程を必ず通す。
  写真の縁に接する塊（影は必ず縁から始まる）と、一番大きい塊に対して小さすぎる塊を捨てる。
  順番も固定する。**塊の選別 → トリミング**。逆にすると、捨てるはずの塊を含んだまま切る。

- **R-004 ビルド成果物をテストが拾うと、直したはずのテストが落ち続ける**:

  **何が起きたか** — テストが「4 passed / 4 failed、ただし 44 tests すべて成功」という
  意味の分からない結果になった。

  **なぜそうなったか** — Electron 側の `tsc` が `src/core` を `dist-electron/` に
  コンパイルしており、その中にテストの `.js` 版も出ていた。
  Vitest が元の `.ts` と生成された `.js` の両方を拾い、`.js` 版が実行時に落ちていた。

  **今後どうするか** — テストの探索範囲を明示し、ビルド出力を必ず除外する
  （`vite.config.ts` の `test.exclude`）。tsc の `include` にテストを混ぜない。
  テスト結果が「ファイル数と件数で食い違う」ときは、まず二重実行を疑う。

- **R-005 生成位置を1点に固定すると、同時に生まれたものが重なって見える**:

  **何が起きたか** — 絵を4枚まとめて取り込んで画面を見たところ、
  **2匹がほぼ完全に重なったまま泳ぎ、1匹にしか見えなかった**。
  自分の絵を探しに来た子どもが見つけられない、という一番避けたい状態。

  **なぜそうなったか** — 生成時の横位置を全て画面中央に固定していた。
  縦位置と速さは散らしていたが、速さの幅が狭く、
  **同じ時間帯に取り込んだ絵どうしは同じ場所を同じ速さで並走した**。
  1匹ずつ見ている限り正しく動くので、テストでも気づけない。

  **今後どうするか** — 画面に同時に出るものを生成するときは、
  **位置を1点に固定しない**。縦横とも散らし、「散らばること」自体をテストで固定する
  （`spawnFish の横位置` のテスト）。
  複数個を同時に出した状態で必ず目視する。1個だけの確認で済ませない。

  **追記（同日・再発）** — 生成位置を散らしたあとも、装飾を足して撮り直したら
  **3匹が重なっていた**。生成時に散らしても、速さが近いと泳ぐうちに合流する。
  「最初に散らす」は十分条件ではない。
  近づきすぎた組が**避け合う**処理を入れて解決した（`separateFish`）。
  避ける強さは勘で決めず、**避けない場合と比べて実測**した
  （50匹で重なりの平均 17.82 組 → 1.50 組）。
  強くすればよいものでもなく、強すぎると反発し合って逆に増えた（5.13 組）。
  この手の定数は、必ず「入れない場合」と比べて決めること。

- **R-006 シルエットは、背後が明るくないと消える**:

  **何が起きたか** — 装飾に沈没船を入れたのに、画面には**帆柱の線だけが宙に浮き、
  船体が丸ごと見えなかった**。砂を明るくして船体は出たが、今度は手前の海藻と
  重なって**ひと続きの黒い塊**になり、やはり船の形が読めなかった。

  **なぜそうなったか** — 暗い塗り（シルエット）は、背後が明るいときにだけ形が読める。
  画面の下は水の色自体が暗いうえ、砂も岩も船も同じ暗い色で塗っていたため、
  **水・砂・船がすべて同じ暗さになり、境界が消えた**。
  重なりも同じ理由で、濃さの等しい物どうしは接した瞬間に輪郭が無くなる。
  「描いていないから見えない」と思い込み、大きさや位置ばかり直していた。

  **今後どうするか** — シルエットで物を見せるときは、次の3つを守る。
  1. **背後を明るくする。** 砂は明るい敷物、その上に乗る物は暗い影絵、という関係にする
  2. **前後で濃さを変える。** 沈没船は手前の海藻より薄くして、奥にあると分からせる
  3. **重ねない。** 重なると輪郭が消える物は、そもそも同じ場所に置かない
     （`placeOutside` で沈没船の前には海藻も岩も生やさない）

  「置いたのに見えない」ときは、その物の大きさや位置ではなく、
  **背後との明るさの差**を疑うこと。
