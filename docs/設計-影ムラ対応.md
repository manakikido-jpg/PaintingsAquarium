# 設計：紙の中の影ムラで取り込みが拒否される問題

- 作成: 2026-09-09
- 状態: **設計のみ。実装は止めている（本人の決定待ち）**
- 関連: R-020（しきい値は写真ごとに自動で選ぶ）/ R-067（縁に触れる絵の直近の修正）/ `src/core/cutout.ts`

---

## 1. 何が起きているか（実測）

一度目のイベントの実物データ（アクアリウム19枚）のうち **1枚が「紙の白がほとんど
消えませんでした」で取り込み拒否**（`diagnoseCutout` の `nothing-removed`）。

絵そのもの（サメ）は問題なし。原因は紙の一部にかかった強い影（テープか撮影時の
影と見られる）。**絵にかぶっていない、まっさらな余白帯**だけを取り出して明るさを
測ると、こう出た。

| 位置（横方向） | 明るさ（value） |
|---|---|
| 左端付近 | 0.32〜0.41 |
| 中央付近 | **0.65**（一番明るい） |
| 右寄り | 0.49〜0.57 |

同じ紙・同じ余白の中で、明るさが **0.32〜0.65** まで揺れている。

## 2. なぜ起きるか

`cutoutPaper`（`src/core/cutout.ts`）は、**写真1枚につき明るさのしきい値を1つ**
自動で選ぶ（`chooseCutoutValue`、R-020）。写真ごとに紙の明るさが違う問題は
これで解決したが、**同じ1枚の中で紙の明るさが場所によって大きく違う**場合には
効かない。しきい値をどこに置いても

- 高くすれば、影の部分の紙が「紙ではない」＝絵として残ってしまう
- 低くすれば、薄い色のクレヨンまで紙と一緒に消えてしまう

の板挟みになる。今回は前者が起き、影が濃すぎて`opaqueRatio > 0.95`（9割5分が
消えずに残る）で拒否された。

**紙の色そのものからの距離（`tintDistance`）は、実は影に強い。** 比べる前に
明るさを揃えてから比べているため（コード内コメント参照）。**弱いのは明るさの
下限判定（`value(r,g,b) < looseValue`）だけ**。これは黒に近い暗い画素を
「紙ではなく絵」と扱うための安全策で、外すことはできない
（外すと暗い塗りつぶしが紙と誤判定されて消える）。

**つまり問題は「明るさの下限」が写真全体で1つの定数になっていること。**

## 3. 案

### 案A（推奨）: 通常の判定で拒否されたときだけ、影を考慮したしきい値で撮り直す

- **平常時（今回の44枚中43枚）は一切触らない。** いまの一発判定（グローバルな
  しきい値の自動探索、R-020）をまず試し、これが**失敗したとき（`nothing-removed`）
  だけ**、次の手を試す。
- 失敗したときの次の手: 画像を粗いブロック（例: 横4×縦3）に分け、ブロックごとに
  「そのブロックの中で一番明るく・彩度の低い画素」を紙の明るさの目安にする
  （いまの `chooseCutoutValue` と同じ考え方を、写真全体ではなくブロック単位でやる）。
  影がかかったブロックは基準が下がり、明るいブロックは基準が変わらない。
- ブロックの境目でしきい値が急に変わると輪郭にギザギザが出るおそれがあるので、
  隣接ブロックの基準をなめらかに補間する。

**利点**: 43/44 の既存の挙動は1画素も変わらない（触るのは失敗経路だけ）。
**欠点**: 実装・検証の手間が増える。ブロックの粒度や補間の仕方に「決め」が要り、
今回のような実物1枚だけでは境界値を決めきれない可能性がある。

### 案B: 直さない。エラー文言はそのままにして、運用でカバーする

いまの拒否メッセージ（「紙とみなす明るさを下げるか、紙全体に光が当たるように
撮り直してください」）は、実は原因を正しく言い当てている。**運営者への案内文書に
「紙に影を作らない（テープの影・撮影者の影に注意）」を1行足すだけ**で終える。

**利点**: リスクがゼロ。**欠点**: 起きるたびに1枚だけ取り込み直しの手間が発生する
（実測 5%）。会場が撮影に慣れてくれば実質さらに減る可能性もある。

### 案C: 案Aの簡易版 — ブロック分割の代わりに、影っぽい暗い帯を検出したら
そこだけ明るさの下限を下げる

案Aの「ブロック格子」の代わりに、**紙の外周の帯（`paperColour` が使っているのと
同じ帯）を細かく分割して、区間ごとの明るさのばらつきを見る**方式。実装はやや
軽いが、外周でしか影の強さを測れないので、絵の内側だけに影がかかるケース
（外周は無事）には効かない。案Aより効く範囲が狭い代わりに書く量も少ない。

## 4. 私の推奨

**案A**。理由:

- 既存の43/44枚・合成回帰33枚に**触れない**設計（失敗時のみ発動）にできるので、
  R-067で踏んだ「直したら別のところが壊れた」を繰り返しにくい。
- 発生率は低い（5%）が、繰り返し性のある本物の原因（テープ・照明配置）なので、
  次のイベントでも起き得る。
- 案Bで様子見するにしても、案Aの実装自体は「失敗時だけ動く」ため急ぐ必要はない。
  **今回は案Bの案内文だけ先に足し、案Aは実物データがもう少し増えてから
  境界値を決めて実装する、という順番も取れる。**

## 5. 決めてほしいこと

- **D-1**: 案A（実装する）／案B（運用でカバーして様子見）／案C（軽い版で妥協）
  のどれで進めるか。
- **D-1 を「案A」にする場合**: ブロックの粒度（横4×縦3を仮案としている）を
  実物データ1枚だけで決め切ってよいか、次のイベントのデータを待つか。
  **私の推奨は「実装だけ先に用意し、既定はオフ／実物2〜3例で境界値を
  合わせてからオン」**（要件定義 D-1「実物が無いと既定値を決め切れない」と同じ考え方）。
