# 動物園：取り込み・保存の繰り返し検証

2026-11-12。レビュー用ブランチ `feat/drawing-zoo`。既存の会場データには触れず、専用フォルダと合成画像で検査した。会場への配布・最新版の公開は行わない。

## 再現して修正した問題

| 問題 | 修正前の確認 | 修正 |
|---|---|---|
| 処理待ち中に監視を再開すると重複保存 | 12枚の受付に対して少なくとも25枚の重複を検出 | 受付予約を監視再開後も保持し、画面の成功・失敗通知で解放。保存側でも同一受付キーは既存の絵を返す。表示一覧も同一idを重ねない |
| 画面再読込で待ち行列の絵を失う | 読込に2秒の遅延を入れた6枚で、再読込後は保存0枚 | 各画面読込完了時に予約をリセットし、元フォルダから未保存分を再受付 |
| 低FPSで登場・退出の時計が遅れる | 表示上限50体に74体を描画。上限10体へ変更して21秒相当進めても61体が残る | 移動用の最大50ms刻みと実時間を分離。修正後は同条件で10体へ戻る |
| 保存失敗で未登録画像・不完全な画像・一時JSONが残る | 台帳リネームの例外と画像途中書込みの例外を注入し、残骸を検出 | 新規保存に失敗したとき、今回の生成画像と一時JSONを片付け、既存の絵と元のエラーを保持 |

## 単体・保存検査

- **591件／38ファイルの単体テストを3回連続で成功**。typecheck/buildも成功。その後の一時JSON清掃は専用3件のテストと最終Windows CIの全591件で確認。
- 20通り×50件、計1000件の受付で、テーマ変更・設定取得失敗・画像処理失敗を混ぜ、成功分の受付順と設定、失敗後の継続を検査。
- 同一受付キーを100回再送しても、台帳1件・画像ファイル1個・最初の色と種類を保持。更新時刻を変えたキーでは別の絵を保存。
- 保存先のエラーを模擬し、既存の台帳・画像を保持し、残骸の除去と再試行成功を確認。実ディスクを満杯にした検査ではなく、ファイルI/Oへの例外注入。

## 実Electronで完了した検査

- 同名・同サイズ上書きを **60回**（ゾウ・ライオン・キリン各20回）。欠落・重複0件。壊れた内容からの正常な上書きも保存でき、最終61枚。
- 画面再読込を **5回**。処理待ちの各6枚、計30枚がすべて正しい種類・テーマで保存され、キーの重複0件。

## 検査方法と限界

`tools/audit-scan-stress.py` は監視再開を挟む連続取り込み、`audit-scan-overwrite.py --rounds 20` は上書き60回、`audit-scan-reload.py --rounds 5` は画面再読込を検査する。専用の空プロファイルと監視フォルダが前提。既存の実データがある場合は中断する。

複数の検証アプリを同時に動かした初回の連続検査は、48枚のうち47枚の時点で120秒の待ち時間を超過。その後48枚すべての保存を確認したが、この回は合格と数えず、検証アプリを終了した単独環境で最初から実行し直す。単独環境でも、人工遅延を入れた検査は60枚のうち57枚の時点で同じ待ち時間を超過し、後から60枚の保存を確認した。表示数が増えた状態では、250msの検査タイマーが約3.86秒に延びた。これらの回は合格に含めず、通常処理（人工遅延0）と区別する。ソフトウェア描画の影響があるため、ここでの処理時間を会場PCの性能値として使わない。通常処理でも50体前後の描画負荷で遅延を確認しており、速度問題は解消済みとしない。会場PCでは保存完了から表示まで5秒以内を別途確認する。

実スキャナ・Windows会場PC・会期と同じ時間の連続稼働、電源断、物理ディスク故障、削除そのものが失敗する保存先は未確認。今回の回数からイベントでの不具合率や「不具合ゼロ」を保証するものではない。

Windows CIも591テストとパッケージ作成が成功（アプリコード `0ce7d32`、[実行記録](https://github.com/manakikido-jpg/PaintingsAquarium/actions/runs/43166003659)）。最新版への公開ステップは実行していない。

通常処理での120枚検査も、72枚まで完了した時点で仮想画面サーバーの停止により中断（`xdpyinfo`で接続不能、サーバープロセス不在を確認）。この実行も120枚完走としては数えず、同じ保存先での再起動・未保存原稿の回復と区別して検証する。

仮想画面を起動し直して同じ保存先で再開し、保存済み72枚の全メタデータが不変であること、未保存の12枚を自動回収して計84枚となること、全件のキーが一意で種類・テーマも正しいことを確認した。

## 最終の追加確認

登場・退出の時計を修正後、594テストとtypecheck/build成功。実Canvasでも上限10体・21秒相当後の描画が10体に戻った。通常処理は、中断後の回復を挟みつつ120枚まで保存し、全件の種類・テーマ・キーの一意性を確認した。120枚を無中断・規定速度で完走した検査ではない。

最終的に120枚の保存を確認したうえでアプリを3回再起動し、全120枚のメタデータ・画像SHA-256・設定がすべて不変だった。通常処理で完了した9回の12枚バッチでは少なくとも27回の監視再開を挟み、重複受付・重複保存0件。中断した1バッチ12枚は再起動で回収した。

[機械可読の結果](checks/zoo-repeated-tests.json)に回数と観測結果を保存した。低FPSの退出は `tools/audit-exit-clock.py`、プロセス再起動と画像ハッシュは `tools/audit-scan-restarts.py` で再検査できる。時計修正後の最終単体テストは594件／39ファイル。Windows CIの最終結果はPRにも記載する。
