# 設計：AIで魚らしい動きを出す

- 作成: 2026-08-18
- 状態: **未着手。①と②が決まるまで実装しない**
- 関連: F-320（いまのしなり）/ 要件定義 §4（AI補正を「やらないこと」に置いている）

---

## 0. 何を作るか（1行）

**取り込んだ瞬間に一度だけ、絵から「体の芯」と「尾びれ」を推定し、
尾びれが付け根から振れるようにする。**

---

## 1. AIにさせること／させないこと

| | |
|---|---|
| **させる** | 取り込み時に1回だけ、絵の**どこが何か**を出す（体の芯・尾びれ・頭の向き） |
| **させない** | **毎フレームの動きを作ること** |

### なぜ毎フレームは無理か

会場の想定は**50匹が同時に泳ぐ**画面で、なめらかに見えるには 60コマ/秒 が要る。

```
50匹 × 60コマ = 毎秒 3,000 回の推論
```

いちばん軽いモデルでも1回 10ms は掛かるので、必要な計算は**実時間の30倍**になる。
GPUを積んだ機械でも成立しない。**動きは今まで通りコードで作る。**

一方、取り込みは **1日30〜100枚**。1枚に3秒かかっても、
写真が届くのは人の手の速さなので詰まらない。
**AIを使ってよいのは、この「1枚につき1回」の場所だけ。**

---

## 2. AIが出すもの（リグ）

絵と一緒に保存する。次に起動したときは再計算しない。

```ts
interface Rig {
  /** 体の芯。頭→尾の順。絵の幅・高さに対する割合（0〜1） */
  readonly spine: readonly { x: number; y: number }[]
  /** 尾びれ。付け根（回転の中心）と、尾びれに含まれる範囲 */
  readonly tail: { pivot: { x: number; y: number }; from: number } | null
  /** 頭がどちら向きか。絵の中での向き */
  readonly headsRight: boolean
  /** 推定の自信（0〜1）。低いときはリグを使わない */
  readonly confidence: number
}
```

### いまとの違い

| | いま（F-320） | リグがある場合 |
|---|---|---|
| 頭がどちらか | **進む向きが頭**と決め打ち | 絵そのものから決まる |
| 波の通り道 | まっすぐの体を仮定 | 体の芯に沿う |
| 尾びれ | 胴体と一緒に上下へずれる | **付け根を軸に振れる** |

「尾びれが振れる」がいちばん見た目に効く。いまは尾も胴体も同じようにずれるので、
**しなってはいるが「ひれが動いている」とは見えない**。

---

## 3. 2つの経路

### A. ローカルに同梱する（推奨）

推論もPCの中で行う。絵は外に出ない。

- **完全オフラインを保てる**（要件定義 §7）
- 費用 0 円。200枚/日でも増えない
- インストーラが大きくなる。`onnxruntime-node` は公開されている
  展開後サイズが **270MB**（全OS・全実行環境ぶん）。
  Windows x64 のCPU向けだけに絞れば減らせるが、**実測していない**。
  **77MB → 120〜250MB** を見込む
- 会場PCのCPUで1枚あたり1〜3秒（**未実測**）

### B. 外部のAIサービスを呼ぶ

- **完全オフラインが壊れる。** 会場のネットが落ちた時点で新しい絵が動かなくなる
- **子どもの絵が外部サービスへ送られる。** 説明が要る話になる
- 1枚2〜10秒 ＋ 通信待ち。200枚/日ぶんの従量課金
- インストーラは 77MB のまま

**推奨は A。** 会場でネットに依存する構成は、当日ネットが落ちた瞬間に展示が止まる。
Bを選ぶ場合は、要件定義 §4 の「完全オフライン」を書き換える必要がある。

---

## 4. 使うモデル（ここが一番読めない）

**既製のモデルで、子どもの絵で学習したものは無い。**
どれも写真で学習しているので、クレヨンの絵を入れたときの精度は**やってみるまで分からない**。

| 候補 | 何をするもの | 懸念 |
|---|---|---|
| 汎用の切り分けモデル（SAM系） | 絵を部品に分ける | 「どれが尾びれか」までは決まらない |
| 輪郭抽出モデル（U^2-Net系） | 物の形を取る | すでに切り抜き済みなので価値が薄い |
| 自前で小さく学習 | 尾びれの位置を直接出す | **正解付きの絵が数百枚要る** |

前例として、Meta の *Animated Drawings*（子どもの描いた**人**の絵に骨を入れて歩かせる）がある。
構成は本設計と同じ「**1回だけ骨を推定 → 動きはコード**」。
ただし**あれは人型専用**で、魚のひれには使えない。

> **だから、まず実物で試す。** モデルを選ぶ前に、
> **実際に子どもが描いた絵の写真が20枚**あれば、当たるかどうかをその日のうちに判定できる。
> 当たらなければ**導入自体を見送る**判断ができる。これが一番安い進め方。
> 必要な写真は `docs/リハーサル手順.md` ③ で撮るものとまったく同じ。

## 5. 外れたときにどうするか

**AIは今の動きを置き換えない。上に載せるだけ。**

```
confidence が低い / リグが無い → いまの F-320 の動き（絵全体がしなる）
confidence が高い             → 体の芯に沿った波 ＋ 尾びれが付け根から振れる
```

こうしておくと、AIが外しても**展示は壊れない**。
四角い絵や虹の絵は、これまで通りしなって泳ぐ。

**逆をやってはいけない。** 「AIが出した部位だけを動かす」形にすると、
外したときに絵が変な場所で折れて、**何も動かないより悪くなる**。

## 6. 検証の順番

1. **実物の絵を20枚撮る**（リハーサル ③ と同時にできる）
2. 候補モデルにかけ、**尾びれを当てられた枚数**を数える
3. 8割当たらなければ、この設計は**採用しない**。理由を R-番号 で残す
4. 当たったら、リグを保存する仕組み → 描画 → fps 実測（50匹）の順に作る

**2 の結果を見るまで、モデルの同梱もインストーラの肥大化も発生しない。**

## 7. 決めてほしいこと

- **① 外部通信を許すか** — 推奨: **許さない（A）**。
  許す場合、要件定義 §4 の「完全オフライン」を書き換える
- **② インストーラが 120〜250MB になってよいか** — 推奨: **よい**。
  配布は GitHub Actions 経由（F-406）なので、大きくなっても手間は変わらない
- **③ 8割当たらなかったら見送ってよいか** — 推奨: **見送る**。
  外れたリグで絵が壊れるくらいなら、いまのしなりのほうが良い
